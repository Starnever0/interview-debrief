### Q1. 你们 RAG 的召回质量是怎么保证的？

**分类**：项目经历 / RAG 召回

**面试官意图**：连续追问三次召回口径（怎么算、bad case 怎么归因、上线后是否回落），可能是在确认这件事是不是他本人做过、有没有量化归因的方法。

补充：也可能只是固定题本里的追问，与回答质量无关。

**我的回答**

> 讲了用 rerank 提效果，召回率大概提升了百分之三十左右。

**评价**（部分命中）

- 踩中考点：方向对，知道 rerank 是主要手段。
- 遗漏：没交代召回率的口径（分母、样本集、统计周期）。
- 表达与结构：先讲了五分钟背景，真正做的事只讲了两句。
- **最该改的一处**：把口径讲清楚：在哪个评测集上、用什么指标、提升了多少。

**更好的答法**

**参考答案**

> 这块我们是先有度量、再有优化的。评测集是从线上真实提问里抽的，160 条，人工标了标准答案，指标看 Recall@5 和 Hit@5。第一轮 badcase 归因下来，六成是专业术语召不到——chunk 切得太碎，一个术语被切成两段就再也匹配不上。所以第二轮改的是检索侧：BM25 和向量双路召回做融合，再过一层 rerank 收敛排序。Recall@5 从 0.71 提到 0.88，Hit@5 到了 95%。上线之后是按周盯回落，重点看新增长尾 query 的命中率。

**指导**：面试官想听的是「你如何度量并归因召回问题」，不是「你用了什么组件」。先讲口径再讲手段；顺序反了会显得只是执行者。

**要点骨架**

1. 评测集怎么构造的、多少条
2. 指标定义：recall@k 还是命中率，分母是什么
3. 主要 bad case 的归因分布
4. 改动后的对比与上线后的监控

**变体 / 追问延伸**

- 若追问「rerank 之后还召不回怎么办」→ 讲兜底：query 改写 + 放宽 k 值，并主动说明代价是延迟上升。
- 只有 30 秒时 → 只讲「评测集口径 + 提升幅度 + 上线怎么监控」三句。

### Q2. 说下一致性哈希，它解决了什么问题？

**分类**：计算机基础八股 / 分布式·一致性哈希

**面试官意图**：单问一题、没有追问，可能是常规基础考察，判断分布式基本功是否扎实。

**更好的答法**

**参考答案**

> 一致性哈希解决的是分布式缓存/存储扩容时数据大规模迁移的问题。普通做法是 hash(key) % N，一旦 N 变化，绝大多数 key 的落点都会变，缓存会大面积失效。一致性哈希把 0~2^32 组织成一个环，节点和 key 都映射到环上，key 顺时针找到的第一个节点就是它的归属。这样增加或删除一个节点，只影响环上相邻的一段区间，而不是全量。它的副作用是节点少时分布不均，所以通常给每个物理节点挂多个虚拟节点来打散。

**指导**：标准八股，按「问题 → 结构 → 效果 → 副作用」四步讲完即可，别停在定义层。

**要点骨架**

1. 普通哈希取模的问题：扩容时几乎全量重分布
2. 一致性哈希的环形结构：key 与节点同环，顺时针找第一个节点
3. 节点增减只影响相邻区间
4. 数据倾斜问题与引入虚拟节点

**变体 / 追问延伸**

- 若追问「虚拟节点挂多少个」→ 一般取物理节点数的 100~200 倍，具体看集群规模与 key 分布。
